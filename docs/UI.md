# Native GNOME UI and backend contract

UUID: `gnome-airpods-companion@dosment.github.io`; extension files live directly in `extension/`.

Frontend calls only absolute `~/.local/bin/gnome-airpods-companion`, with separate argv arguments, asynchronously. Status every 5 seconds; no shell interpolation. Product schema v1 applies.

## Normalized Apple contract (backend alignment)

`apple` contains `available: boolean`, `stale: boolean` (optional; true disables writes), `error: string|null`, `battery: {left?,right?,case?,headset?}`, `capabilities: {noise_modes: ["off","anc","transparency","adaptive"], conversation_awareness: boolean, one_bud_anc: boolean, ear_detection: boolean, adaptive_level: boolean}`, and `state: {noise_mode: string|null, conversation_awareness: boolean|null, one_bud_anc: boolean|null, ear_detection: "one"|"both"|"off"|null, adaptive_level: number|null}`. Battery entries: `{available:boolean, level:number|null, charging:boolean, in_ear:boolean, stale:boolean}`. Missing battery readings display Unavailable, never zero. Stale readings are explicitly marked; `freshness:unknown` displays “Observation age unknown.” Snapshot age and daemon liveness cannot establish battery measurement freshness. Optional `is_headset:true` selects one battery instead of buds/case. Absent capabilities grant no controls. Ear detection requires explicit backend support (upstream has behavior state but no supports-ear boolean).

Inspected pinned upstream `fff7fec600a5b9a61cdb40e93eccbcceb4b8f824` README, Model.js and daemon/librepods-ctl.cpp. Upstream `noise_mode` is 0=off, 1=anc, 2=transparency, 3=adaptive; `ear_detection_behavior` 0=one, 1=both, 2=off. Upstream `conversational_awareness` maps to normalized `conversation_awareness`; `one_bud_anc_mode` to `one_bud_anc`; `adaptive_noise_level` to `adaptive_level`. Battery objects are top-level upstream, with `available`, `level`, `charging`, `in_ear`; missing/available:false must not be treated as measured 0%. Do not adopt upstream's permissive old-daemon capability fallbacks.

Actual inspected ctl verbs: `noise:off|anc|transparency|adaptive`, `ca:on|off`, `onebud:on|off`, `ear:one|both|off`, `adaptive:N` (integer 0..100; only adaptive active). UI passes these as `apple VERB`. No forget, cycle, arbitrary verbs or protocol packets. ctl successful exit is delivery, NOT confirmed hardware state; UI waits for status readback, never optimistically fabricates it.

## Presentation and lifecycle

Uses standard GNOME `PanelMenu.Button`, `PopupMenu` items, submenus and symbolic headphones icon; no Apple outlines, custom fonts, GTK window or stylesheet. Kept visible when disconnected so Connect and errors remain reachable. Desired Music/Meeting and actual profile are separate lines; selecting a desired mode never optimistically changes readback. Listening state, toggles and ear policy show Unknown until reported. CA, one-bud ANC and adaptive-level labels explicitly say “Reported”; these are daemon preferences, not verified hardware settings. Ear behavior is labelled “Local policy.” Voxtype displays desired intent separately from effective launch routing (or Unknown), wrapper receipt status, and an explicit coordinated idle restart requirement; finishing dictation does not apply queued changes. Even a matching live launch says actual capture is not verified. Adaptive intensity offers explicit 0/25/50/75/100 percent presets while Adaptive is active. Microphone pin choices are the current PipeWire `microphones[].name` values, passed as one literal argv token. A missing pinned microphone is identified rather than silently switching policy.

One outstanding CLI process maximum, 15-second timeout, async UTF-8 communication, 5-second status polling and refresh on menu opening. No file monitors are needed. Poll timer, deadline timer, cancellable, subprocess and all menu signals are disposed on disable; each enable gets a fresh controller, so old callbacks cannot touch it. Status failures retain previous telemetry with explicit stale indication and disable all writes. The next successful status restores controls; command errors remain visible until another action. Render-equivalent status responses (ignoring continuously changing `age_seconds`) do not rebuild the menu, preserving keyboard focus during idle polling; stale/control-state transitions still rebuild. A backend change may rebuild open submenus; pending actions disable controls. Backend must independently serialize mutations and enforce capability and source validation.

## Verification and remaining user acceptance

- `node --test tests/frontend*.test.mjs`: pure parser/schema, missing/stale battery, normalized capability gating, literal argv and CLI error tests; additional mocked GNOME/Gio controller tests check no overlap, disable cleanup, stale failure behavior, timeout and no optimistic mode updates. Pure model behavior was implemented in observed RED/GREEN slices. Controller tests use fakes and do not prove GNOME loading.
- `node --check extension/extension.js` and `node --check extension/model.js`: syntax only.
- `gjs -m extension/model.js`: real installed GJS can load the pure ES module.
- Real Gio async `communicate_utf8_async`/finish tuple and exit-status contract checked with harmless `/usr/bin/printf`, not the companion or Bluetooth.
- Installed `gnome-shell --version` reports 50.1. Required `PanelMenu.Button`, popup menu items, `setSensitive`, `setOrnament`, `addMenuItem`, `removeAll` and resource paths were checked in `/usr/lib/gnome-shell/libshell-18.so` using `gresource extract`; this is API inspection, not a running extension test.

No install, enable, GUI automation, hardware controls, recording, commit or push performed for this frontend task. Real GNOME loading remains unverified: install the extension with the agreed installer, let the user enable it, and on Wayland log out/in if Shell has not discovered it (do not restart Shell via Alt-F2 r). `gjs extension/extension.js` is not a valid GNOME load test because standalone GJS lacks Shell's resource/global environment. User must verify panel rendering, keyboard submenu access, current/desired profile readback, real battery and supported controls, default/pinned Voxtype routing and disable/re-enable. Command success does not confirm hardware acceptance; the pinned ctl generally acknowledges socket delivery, not device application. Backend normalization and hardware readback remain separate acceptance gates.
